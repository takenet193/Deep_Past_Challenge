# Deep Past Challenge - Akkadian MT 前処理 & アンサンブル実装リファレンス

元ノートブック: https://www.kaggle.com/code/carp0308/akkadian-mt-preprocessing-ensemble-inference

Deep Past Challenge 向けに「**仕様準拠の前処理**」「**評価指標実装（BLEU + chrF++ 幾何平均）**」「**アンサンブル推論**」「**Kaggle 環境対応**」までを 1 つにまとめた実装のリファレンス。
ここではコードではなく、**設計と振る舞い**をテキストでまとめる。

## 1. ノートブック全体の位置づけ

- **目的**:
  - Deep Past Challenge の**公式仕様に完全準拠**した前処理・推論・提出ファイル作成を行うこと。
  - インターネット無効の Kaggle 本番環境でも動くように設計すること。
- 主な機能:
  - Contest 仕様に沿った **Akkadian 転写テキストの前処理**
  - **BLEU + chrF++ の幾何平均**による評価指標関数の実装
  - 複数モデル・自己アンサンブルによる **推論安定化（Ensemble + Self-Ensemble）**
  - `submission.csv` をコンテスト仕様に合わせて生成・検証

## 2. 前処理 (OptimizedPreprocessor) の詳細

### 2.1 現代的な書記記号の処理

- 削除または空白に変換する記号:
  - `!` : 確実読み（certain reading）
  - `?` : 不確実読み（uncertain reading）
  - `/` : 行区切り (line divider)
  - `:` `.` : 語区切り (word divider)
- 方針:
  - **モデルにとってノイズになる注記は削る**
  - 語・行の境界としての役割は空白で吸収する

### 2.2 挿入・誤記・コメントの扱い

- `<...>` : 書記の挿入 (scribal insertions)
  - **中身は残し、角括弧だけ除去**。
- `<<...>>` : 誤った記号 (errant signs)
  - 記号全体を削除（内容も含めて消す）。
- `[...]` : 欠損箇所だが中身が分かるケース
  - 中身は残して角括弧だけ除去。
- `(...)` : 欠損や消去に関するコメント
  - 説明コメントなので **文字列ごと削除**。

### 2.3 欠損（Gap）の正規化

- 目的: 欠損の表現揺れを抑え、モデルが「ここは欠損」とだけ認識できるようにする。
- 代表的な正規化ルール:
  - `[x]`, `xx`, `x` など → `<gap>`
  - `...`, `…`, `[... …]` など → `<big_gap>`
- 追加のクリーンアップ:
  - `<gap> <gap>` → `<gap>` に統合
  - `<big_gap> <big_gap>` → `<big_gap>` に統合

### 2.4 行番号の削除

- 行頭・行中に現れる行番号を削除:
  - 行頭: `1'`, `5''` など → 正規表現でまとめて除去。
  - 行中の行番号もパターンにマッチしたら空白に置き換え。
- 理由:
  - 行番号は翻訳内容には寄与しないメタ情報であり、モデルにとってノイズとなる。

### 2.5 Unicode 正規化 & 添え字の扱い

- 文字レベルの正規化（コンテスト仕様に合わせる）:
  - `ḫ/Ḫ → h/H` : H 系のバリエーションを 1 種に統一。
  - アクセント付き母音: `á, à, é, è, í, ì, ú, ù → a2, a3, e2, e3, i2, i3, u2, u3`。
  - 子音: `š, Š, ṣ, Ṣ, ṭ, Ṭ → sz, SZ, s,, S,, t,, T,` など内部表記に変換。
  - 下付き数字: `₀-₉, ₓ → 0-9, x`。
- 「文字 + 下付き数字」の正規化:
  - 例: `lu₂` のようなパターンを検出し、`₂` を `2` に置き換える。

### 2.6 決定詞（Determinatives）の扱い

- `{...}` で囲まれた **決定詞は保持** する。
- カバーしている代表的な決定詞（18 種）:
  - `{d}`: 神名
  - `{mul}`: 星・星座
  - `{ki}`: 地名・場所
  - `{lu₂}`: 人物・職業
  - `{e₂}`: 建物・施設（神殿・宮殿）
  - `{uru}`: 集落・都市
  - `{kur}`: 国・領域・山
  - `{mi}` / `{m}`: 女性名 / 男性名
  - `{geš}` / `{ĝeš}`: 木・木製品
  - `{tug₂}`: 織物
  - `{dub}`: 粘土板・文書
  - `{id₂}`: 河川・運河
  - `{mušen}`: 鳥
  - `{na₄}`: 石
  - `{kuš}`: 皮革・毛皮
  - `{u₂}`: 植物
- 方針:
  - 決定詞は**意味情報として重要**なので、削らず残す。

### 2.7 仕上げ

- 余分な空白の削減: 連続スペースを 1 つにまとめる。
- 前後の空白を `strip()` で削除。

## 3. 評価指標の実装 (BLEU + chrF++ 幾何平均)

- ライブラリ: `sacrebleu` を使用。
- BLEU:
  - `sacrebleu.corpus_bleu(predictions, [references])` でコーパスレベルの BLEU を計算。
- chrF++:
  - `sacrebleu.corpus_chrf(predictions, [references])` で chrF++ を計算。
- 幾何平均（コンテスト公式メトリクス）:
  - BLEU 値を `B`, chrF++ を `C` としたとき、
  - \( \text{GM} = \sqrt{B \times C} \)
  - どちらかが 0 以下のときは 0 として扱う実装になっている。

## 4. モデル・アンサンブル設計

### 4.1 モデル候補とスコアリング

- モデルパスのリストから **優先度スコア** を計算し、最大 2 モデルを選択:
  - Akkadian 特化モデル: +100 点
  - Base / Large / Small などのサイズ別加点
  - ByT5 系: +60 点, T5 系: +40 点
  - パス中に `akkadian` を含む深さなども加点
- スコア順にソートし、上位 1〜2 モデルを推論に使用。

### 4.2 Ensemble 推論 (ModelEnsemble)

- 各モデルについて:
  - `generate()` で翻訳を生成。
  - `tokenizer.batch_decode()` でテキスト化。
  - 必要に応じてポストプロセスを適用。
- 統合ロジック:
  - 各モデル出力に対して `score_translation()` で品質スコアを計算。
  - モデルごとの重みを掛けて **重み付きスコア** を求め、最大のものを採用。

### 4.3 Self-Ensemble（単一モデル時）

- 単一モデルしかない場合は、**複数回サンプリング推論**して自己アンサンブルを行う:
  - `num_runs` 回だけ `do_sample=True` で生成。
  - 戦略:
    - `voting`: 出現頻度の高い翻訳を採用。
    - `longest`: 最長の翻訳を採用。
- 目的:
  - サンプリングにより揺らぎを持たせ、安定した翻訳を選び出す。

## 5. ポストプロセス & 品質スコアリング

### 5.1 ポストプロセス (EnhancedPostprocessor)

- 出力側で行う主な処理:
  - 制御文字や問題のある Unicode の削除。
  - 残った `[]`, `<>`, 決定詞 `{}` などを文脈に応じて整理。
  - `<gap>`, `<big_gap>` の整理（連続を 1 つにまとめるなど）。
  - 単語の重複削減、空白・句読点周りのクリーンアップ。
  - 先頭大文字・文末句読点 (`.?!`) の補正。
  - 短すぎる文やギャップだらけの文は、
    - "The tablet contains fragmentary text." のような定型文に差し替え。

### 5.2 品質スコアリング (score_translation)

- スコアに効く要素:
  - 長さ（極端に短い/長いと減点、適度な長さで加点）。
  - 文頭大文字・文末句読点の有無。
  - ドメイン固有語彙（palace, temple, king, silver, tablet など）の出現。
  - 固有名詞らしきパターン（先頭大文字・ALL CAPS ロゴグラム）。
- 減点対象:
  - `???`, `xxx`, fragmentary/broken/illegible/damaged などの過多。
  - `<gap>`, `<big_gap>` の比率が高すぎる場合。

## 6. Kaggle 環境での動作設計

- **インターネット OFF 前提** の Kaggle 競技環境を想定。
- モデル/トークナイザは事前に Hugging Face からダウンロードし、
  Kaggle Datasets としてアップロード → `/kaggle/input/...` 配下から読み込む。
- データパスの自動検出:
  - `test.csv` や外部提出ファイル `submission.csv` を複数の候補パスから探索し、
    見つかったものを使用。
- エラー時のフォールバック:
  - モデル未検出時は **デモモード** としてダミー翻訳を生成。
  - DataLoader 作成失敗時は worker 数を減らして再試行。

## 7. 提出ファイル (`submission.csv`) 生成と検証

- `id, translation` の 2 カラムで DataFrame を構成し、`submission.csv` に保存。
- 最終チェック:
  - NULL / 空文字 / 重複 ID の有無。
  - 1 行 1 文（単一文）で終端に `.?!` が付いているかを簡易チェック。
  - 長さ・品質スコアの統計を出力して sanity check。

## 8. このノートの使いどころ

- **ベースライン EDA / 前処理設計タスク** で参照:
  - どの記号を削るか / 残すか、どこまで Unicode を正規化するかの参考にする。
  - `OptimizedPreprocessor` のルールから、**自分のベースライン用にどこまで簡略化するか**を決める。
- **将来の高性能モデル実装**で参照:
  - 前処理・ポスト処理の設計をこのノートを軸に比較し、「どこを変えたか」を意識できるようにする。
- **Kaggle 提出用ノートブックを書くとき**のチェックリストとして:
  - 前処理・評価・アンサンブル・submission 生成の各ステップが抜けていないか確認するためのリファレンス。
